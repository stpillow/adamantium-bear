## 1. Context

You are building a personal, single-user training app for Shawn. He is 13 weeks out from a multi-ligament knee sprain and starting a 12-week return-to-sport program: three full-body lifts a week at Planet Fitness, three runs, and criteria-gated phases. The app replaces the notebook: it says what to do today, logs what happened, reads the knee's response, and decides what the next session looks like.

It runs on an iPhone at the gym, often with weak signal, one-handed, inside 60-second rest windows. Every logging interaction has to be doable in under 10 seconds without reading.

Two files are the source of truth, both in this repo:

- docs/program.md: the training program (phases, sessions, exercises, cues, gates, mileage plan, substitutions). Transcribe it into seed data once, carefully; don't parse it at runtime and don't improve the training content. Questions about the program go on a list for Shawn, not into the code.
- PROMPT.md: this file, which owns app behavior. Where the two disagree on training content, program.md wins; on app behavior, this file wins.

## 4. Rules engine

Everything below lives in src/rules/ as pure functions with Vitest cases, including one test per worked example at the end. The UI never decides anything; it asks the engine.

1. Session reading, per exercise. Take the painDuring values for that exercise (per set if enabled, otherwise the one value per exercise). Max of 3 or under and not climbing: clean. 4–5, or climbing: hold. Over 5, or a set marked stopped for sharp joint-line pain: back-off. Climbing means pain rose by 2 or more points across consecutive sets.
2. Morning reading. stiffnessUnder30Min true and nothing else flagged: clean. worseThanYesterday true with no swelling, no warmth and painChangePoints under 2: hold. visibleSwelling, warmth, or painChangePoints of 2 or more: back-off. Any redFlags entry on a check for today: red-flag state (rule 9).
3. Combined reading. For each exercise in the last workout, the combined reading is the worse of its session reading and the workout's morning reading. A workout with no morning check within 36 hours reads as hold for every exercise, not clean: unknown isn't clean. A check logged late is dated the morning it describes, so it counts as within the window and reads exactly as one logged that morning.
4. Next prescription, per exercise and side. Inputs: the last two combined readings, the last set logs, the slot's prescription. Clean twice in a row and every set hit repsMax at RPE 8 or under: load plus one increment, reps reset to repsMin. Clean twice but short of repsMax: same load, target repsMax. Clean once: same load, same target. Hold: repeat the last session's loads and reps exactly. Back-off: load times 0.75 rounded down to the increment, or the previous substitution when loadType is bodyweight or step-height. height-then-load raises step height one increment before any load is added; range-then-load (leg extension) moves the range stop 90° to 45° to 30° before load. Deload weeks skip progression entirely. Inside a down period, clean twice repeats the last session's load and target instead of stepping up (rule 11).
5. Unilateral budget. The injured side is logged first. The healthy side's target reps for each set equal the injured side's completed reps for that set; its load may match or exceed. Symmetry is the injured value divided by the other side's value, shown as a percent — except on a timed test, where lower is better, so it is the other side's value divided by the injured side's (rule 8).
6. Deload. Weeks 4, 8 and 12 counted from startDate: sets times two-thirds rounded down, minimum 2; loads unchanged; isDeload true on the Workout. Progression resumes the week after, from the loads in use before the deload. A deload week inside a down period deloads as ever; the pause adds nothing (rule 11).
7. Mileage. Each week's target comes from MileagePlan. If any run or workout in the current week reads hold or back-off, next week's target is capped at this week's actual miles. A week whose Monday a down period covers doesn't step up: its target holds at last week's, and the weeks after one climb back one plan step a week, the lower of that and this rule's number standing (rule 11). The long run's suggested distance is 40% of the week's target rounded to the nearest half mile; the other two runs split the remainder. Swap runs count as sessions and add no miles.
8. Gates. Each gate is a checklist. Auto-evaluated items: two consecutive clean weeks (14 days with no hold or back-off on any subject), symmetry thresholds from GateTest entries (80% for gate 1, 90% for gates 2 and 3), 20 single-leg calf raises each side, no swelling flagged for 14 days, and on gate 3 an ACL-RSI score of 76 or better read from the latest stored questionnaire entry (the strict published threshold; "no questionnaire entered yet" fails in words). Gate 3's hop battery is four tests: single, triple and crossover hop for distance plus the 6-meter timed hop — for the timed hop, best = the FASTEST trial in seconds and symmetry inverts to other ÷ injured, so a slower injured side reads under 100%; 0 is not a time and is refused in words. Manual items: step-down video pass, ortho or PT sign-off, "would trust it at full speed" (kept, separate from ACL-RSI). A gate passes when every item passes; the phase advances only when the user confirms, never automatically, and not while a down period covers today, the day it was ended included (rule 11). KOOS is never a gate item: no gate may read a KOOS number. An added or extra-time exercise's sets count for the load-test prefill and the calf-raise item only when it is the same exercise the item tests (exact id; a substitution or similar movement never), and the prefill reads both sides from one slot, the least symmetric slot when the exercise ran on two that day (Batch C, PROGRAM-QUESTIONS 168).
9. Red flags. Any redFlags entry on a morning check for today puts the app in a red-flag state: the Today screen shows "Stop. Call the ortho or PT." with the flagged items, and progression suggestions are suspended until the user clears the state from Settings with a note. A check logged late, for a past morning, never does: its flags show as a note in words (keeping the program's "call the ortho or PT") on Today, beside Gates' Advance, on the Week row and on the check's result, and it suspends nothing (Batch D, PROGRAM-QUESTIONS 175). The takeover supersedes a down period, which keeps running underneath it (rule 11). The list of flags is the Red flags section of program.md.
10. Week and day. week = floor((date − startDate) / 7 days) + 1, dates read in the user's time zone (Settings; America/New_York by default). The scheduled session for a date comes from the weekly template (Mon run MBR, Tue A, Wed run easy, Thu B, Fri run long, Sat C, Sun off); the user can move a session to another day in the same week.
11. Down period (Batch E, Shawn's Nov 8 decision 6; program.md's loading rules; PROGRAM-QUESTIONS 181 to 189). A declared "not feeling 100%" stretch of 3 to 14 days, starting the day it is declared, for illness or life stress, not the knee. While a day is inside one, progression pauses and the readings stay real: an exercise that reads clean twice repeats its last load and target (basis `paused`, "Down period: progression paused until Friday Nov 20"), a slot on its easier version stays there, the phase-week bands (the single-leg plyo, the snap-downs, the tempo) stay where they were when it began and resume from there after it, a week at a time, never the calendar's jump, and the week's run target holds (rule 7). Hold, back-off, the whole-knee back-off, deloads and the red flag apply exactly as outside one; a pause can only make a prescription equal or lower, never higher. Every session inside one is read and stored as normal, so a clean one still counts toward clean twice afterwards. The pause applies to the day planned, so a session logged late into a day inside one plans paused. It can be ended early (the day ended still counts), made longer up to 14 days from its start, or kept going on the day it was ended; it is never backdated, and an import never lifts one the phone has standing.

Worked examples to encode as tests:

- Leg press, Phase 1: sets of 12, 12, 12 at RPE 7 with pain 2, 2, 2; morning clean; previous session also clean and at repsMax. Next: plus one plate, 3 × 10.
- Step-up: 3 × 10 with 20 lb, clean twice at 6 in. Next: 8 in. at 20 lb (height before load).
- Bulgarian split squat, injured side completes 8, 8, 7. Healthy side targets 8, 8, 7.
- Week 4, a 3 × 10 slot. Prescribed: 2 × 10 at the same load.
- Week 2's Friday run reads hold. Week 3 target becomes week 2's actual miles, not 12.
- Hop test: injured best 56 in., other side 62 in. Symmetry 90.3%, passes gate 3's 90% line.
- 6-meter timed hop: injured fastest 2.3 s, other side 2.1 s. Symmetry is 2.1 ÷ 2.3 = 91.3%, passes gate 3's 90% line (the ratio inverts because lower is better).
- Down period: leg press clean twice at the top of the range, 8 plates × 12 at RPE 7; a down period covers the next session. Next: 8 plates × 12 again, basis paused, not plus one plate.

## 6. Build plan

Seven milestones, each a PR with a preview deploy and a three-line demo note. Stop for review at the end of each; don't start the next until Shawn says go.

1. M0, Scaffold. Repo, Vite + React + TypeScript strict + Tailwind, vite-plugin-pwa with an offline-first service worker, Dexie with an empty schema, CLAUDE.md, Vercel project with preview deploys. Done when the app installs to an iPhone home screen and loads in airplane mode after one visit.
2. M1, Seed data. Zod schemas for section 3; data/program.json transcribed by hand from docs/program.md: all nine session templates, every slot's cues and substitutions, the three gates, the 12-week mileage plan, the red-flag list, and the exercise catalog with increments. A npm run program -- --week 5 --session B script prints a session. Done when the schema validates, the script output matches program.md on a spot check of all three phases, and PROGRAM-QUESTIONS.md lists anything ambiguous.
3. M2, Rules engine. src/rules/ with every rule in section 4 and Vitest coverage including the worked examples. Done when tests are green and no rule lives outside the module.
4. M3, The daily loop. Today, Session runner, Morning check, and the Settings basics. Done when Shawn can run Session A on his phone end to end, do a morning check, and watch the next Session A's prescriptions change according to the reading.
5. M4, Running. Run logger, Week screen, miles against plan, the hold cap. Done when three logged runs show against the week's target and a hold reading caps the following week.
6. M5, Gates and progress. Gates screen with live evaluation, hop-test entry, Progress charts. Done when gate 1 evaluates from logged data alone and the hop-test symmetry matches the worked example.
7. M6, Hardening. Program editor, export and import, offline QA on a real phone at the gym, a Lighthouse PWA audit, the Playwright smoke test for the Session runner. Done when export, wipe, import restores everything, and a full Session B gets logged on cellular with the screen locked between sets.

Definition of done for v1: Shawn runs week 1 of the program entirely from the app, on his phone, with morning check-ins deciding the loads for week 2.

## 7. Working agreements

How to operate, from the first message on:

1. Read docs/program.md and this file in full. Then write PLAN.md: the seven milestones expanded into tasks with checkboxes, a Decisions log, and the PROGRAM-QUESTIONS list. No code before PLAN.md exists.
2. Ask the questions in section 9 in your first reply, all at once, with your proposed default beside each. If Shawn answers "defaults", proceed with them and record that in the Decisions log.
3. Keep CLAUDE.md current: stack, commands (dev, test, build, deploy), folder layout, the domain glossary (slot, reading, clean, hold, back-off, gate, deload, symmetry), and the two rules that are not negotiable: logic only in src/rules, and no color-only meaning in the UI.
4. One commit per task, one PR per milestone, conventional commit messages, the preview URL in the PR description, and a three-line demo note: what to tap, what to expect, what's not done.
5. Tests before UI for anything in section 4. A rule change without a test change is a bug.
